# Plan: Audit remediation (2026-10-23)

## 0. Purpose

A bug and security audit of the whole tree (every non-test file under
`internal/` and `cmd/`) on 2026-10-23 found five high-severity issues, about
fifteen medium ones and a tail of low ones. `go vet` and `go test ./...` were
clean at the time; none of the findings is caught by the existing suite.
`govulncheck` could not run (no route to vuln.go.dev from the audit host), so
dependency CVEs are **not** covered — run it from a connected host as part of
Phase 0.

This document is the fix plan. Each item states the defect, the chosen fix,
the files it touches, the regression test that pins it, and any decision that
had to be made. Items are grouped into phases ordered by the damage they can
do; within a phase they are independent and can land as separate commits.

Revised the same day after a second pass that checked every item against the
source and against the vendored sabre code under `dav/`. Every defect held
up; about a third of the fixes did not. Where the first draft was wrong the
item now says so in a **Correction** paragraph so the reasoning is not lost.

The theme across the high items is the same one the port keeps meeting: sabre
runs each request in a PHP process with a `memory_limit` and a fresh plugin
instance, so an unbounded loop or a per-request cache only hurts that request.
calserver is one long-lived process, so every "sabre does the same" below is
a real outage or a real leak here even where it is parity.

## 1. Hard constraints

- **Shared database.** sabre reads the same rows. Any change to what
  `Denormalize` stores (item 3.5) must stay readable by sabre's
  `firstoccurence`/`lastoccurence` consumers; we only ever store *correct*
  bounds or refuse the PUT, never a new encoding.
- **Parity first, divergence documented.** Where a fix changes an observable
  response that the corpus pins (`internal/corpus/runner_test.go`), the record
  moves to an explicit "deliberate divergence" list with the reason, the way
  `AddVTimezones` already is.
- **No new config knobs unless the value is genuinely deployment-specific.**
  Caps that exist to stop a crash are constants with a comment; only the push
  per-principal limit (3.3) and the attendee cap (4.4) are tunable.
- **Fail closed on the mail paths.** A send the server cannot attribute to the
  right identity is discarded with a terminal SCHEDULE-STATUS, never silently
  rerouted (3.5 is the instance of this).

## 2. Phase 0 — before any code

### 3.1 Free-busy and time-range recurrence expansion is unbounded

**Defect.** `ical/freebusy.go:253` (`eventBusyPeriods`) and
`ical/timerange.go:53` (`EventInTimeRange`) iterate a rule up to
`maxTimeRangeScan = 1_000_000` per object, the former allocating a
`busyPeriod` per step. The comment says the window end bounds the loop, but
the window is client-chosen: `plugin_reports.go:56` rejects a free-busy
REPORT with *no* `time-range` element, but an empty `<time-range/>` passes
and `query.go:386` defaults it to 1900–3000; `schedule_freebusy.go:97` uses
the outbox VFREEBUSY's DTSTART/DTEND verbatim. A handful of `FREQ=SECONDLY`
events plus one REPORT is an OOM.

**Fix.**
- Clamp the free-busy window to **`maxFreeBusySpan = 366 days`**. A
  free-busy REPORT with a wider span (or an open-ended one) is answered
  `403 Forbidden` with a `{DAV:}error` body naming the limit. An outbox
  VFREEBUSY POST with a wider span answers every recipient with
  `schedule-response` status `5.3` carrying the same message. The window is
  never silently truncated (Decision D1).
- Replace `maxTimeRangeScan` with two budgets in `EventInTimeRange` and
  `eventBusyPeriods`: a cheap **pre-window** iteration budget
  (`maxPreWindowScan = 100_000`, no allocation per step) spent skipping
  instances that end before the window start, and an **in-window** budget of
  `maxRecurrences` (3500) instances actually produced. When either budget runs
  out inside the window the function returns `ErrTooManyInstances` and the
  caller treats the object as matching (time-range) or emits one busy period
  covering the rest of the window (free-busy) — conservative in both
  directions, and never more than 3500 allocations per object.
- `schedule_delivery.go:314` (auto-schedule conflict check) inherits the same
  bound through `eventBusyPeriods`.

**Correction.** The first draft counted all 3500 instances from DTSTART. That
misfires on any daily rule older than ~9.5 years and any hourly rule older
than five months: the free-busy fallback would then mark the user busy for
the rest of every window, permanently. Counting only in-window instances
toward the cap keeps the fallback reachable only by genuinely dense rules.
Note also that sabre's `EventIterator::valid()` throws
`MaxInstancesExceededException` after `Settings::$maxRecurrences` (3500)
*including* in `VEvent::isInTimeRange`, because `fastForward` iterates
rather than jumps; the comment in `timerange.go:48-52` claiming sabre has no
such cap is wrong and should be rewritten with this item.

**Files.** `internal/caldav/ical/timerange.go`, `ical/freebusy.go`,
`caldav/query.go` (`TimeRange.bounds`), `caldav/plugin_reports.go`,
`caldav/schedule_freebusy.go`.

**Tests.** `freebusy_test.go`: `secondly-forever.ics` with a one-year window
completes under 50 ms and allocates < 1 MB (use `testing.AllocsPerRun` or a
`runtime.MemStats` delta). `plugin_reports_test.go`: free-busy REPORT with no
time-range → 403; with a 400-day range → 403; with 365 days → 200.
`schedule_freebusy_test.go`: outbox POST with a 10-year VFREEBUSY → every
recipient `5.3`.

### 3.2 VALARM `REPEAT` drives an unbounded loop

**Defect.** `ical/timerange.go:355` and `:388` run `for i := 0; i <= repeat`
with `repeat` from `Prop.Int()` (64-bit) and no exit once `occ` passes
`end`. `REPEAT:9223372036854775807` pins a core forever on any VALARM
time-range query; PUT never looks at VALARM.

**Fix.**
- In both loops, `break` as soon as `occ` is at or after `end` (the sequence
  is monotonic because `DURATION` must be positive per RFC 5545; treat a
  zero or negative duration as a single occurrence).
- Cap `repeat` at **`maxAlarmRepeat = 3500`** after parsing; larger values
  are treated as 3500 (the alarm still matches the window if any of the first
  3500 repetitions does, which is the only observable effect).

**Correction.** The first draft also rejected at PUT time a `REPEAT` that
does not parse, or that has no `DURATION` beside it. Dropped: sabre's
`VAlarm::isInTimeRange` ignores REPEAT without DURATION and PHP's `(int)` cast
reads `REPEAT:abc` as 0, so such objects exist in sabre-written calendars and
a client re-syncing them would fail forever. Once the loop is bounded the
validation buys nothing.

**Files.** `internal/caldav/ical/timerange.go`.

**Tests.** `timerange_test.go`: `alarm-repeat-max.ics` against a one-day
window returns within 1 ms; a `REPEAT:3` alarm whose second repetition falls
inside the window still matches (no behaviour regression); `REPEAT:abc` and
`REPEAT` without `DURATION` behave as sabre (single occurrence).

### 3.3 Push worker: one subscriber stalls everyone; endpoint is blind SSRF

**Defect.** `push/worker.go:188` sends to every subscriber sequentially from
the single dispatch goroutine with the long-lived `Run` context, and
`push/sender.go:30` leaves `webpush.Options.HTTPClient` nil, which is a
client with no timeout. A `push-resource` pointing at a tarpit blocks
dispatch forever; the 256-slot payload channel then fills and no collection
delivers until restart. `plugin.go:147` accepts any URL as the endpoint, so
every authenticated user can make the server POST to internal addresses.
`store.go:20` has no per-principal cap.

**Fix.**
- `WebPushSender` gets an `http.Client{Timeout: 10 * time.Second}` with a
  transport whose `DialContext` refuses loopback, link-local, RFC 1918 and
  ULA destinations after resolution (resolve, check every returned IP, then
  dial the checked IP — the standard anti-rebinding shape). Keep it in a
  small `safedial` helper in `internal/push` with a table-driven test; it is
  the only outbound-to-arbitrary-host client in the tree, so it does not
  need to be shared.
- `worker.dispatch` sends through a bounded worker pool (**8** concurrent
  sends, `errgroup.SetLimit`) with a **15 s** per-send context, so a slow
  endpoint delays at most its own notification.
- Registration (`plugin.go` POST handler): require `https` scheme, reject a
  host that is an IP literal or resolves only to a blocked range (the same
  helper), and enforce **`MaxSubscriptionsPerPrincipal = 50`** (config
  `[push] max_subscriptions`, default 50) counted in `store.go` inside the
  upsert transaction. Over the cap → `403` with a `{DAV:}error` body naming
  the limit.
- Log a push send that exceeds 5 s at Warn so a slow push service is
  visible before it is a stall.

**Files.** `internal/push/safedial.go` (new), `push/sender.go`,
`push/worker.go`, `push/plugin.go`, `push/store.go`, `push/push.go`,
`internal/config/config.go` + `config/shared.go` (one field),
`internal/server/server.go` (plumb it).

**Tests.** `sender_test.go`: `safedial` table (127.0.0.1, 10.0.0.1,
169.254.169.254, `[::1]`, `fd00::1` rejected; a public IP accepted; a name
resolving to both a public and a private address rejected).
`worker_test.go`: a fake sender that blocks on one subscription does not
delay delivery to another collection by more than the per-send timeout.
`plugin_test.go`: `http://` endpoint → 403; 51st subscription → 403.

### 3.4 `GET ?export` leaks CLASS:PRIVATE/CONFIDENTIAL to sharees

**Defect.** `export.go:170` collects `obj.CalendarData` straight from the
backend. The only redaction point is `CalendarObject.viewData()`
(`nodes.go:565`), which export never goes through, so a read-only sharee gets
the full object the normal GET hides.

**Fix.** Route every blob through the same decision the node makes.
`exportBlobs` already receives `calNode *Calendar`, and `viewData` keys off
`Calendar.readOnly()`, so apply `ical.RedactRestricted` in `exportBlobs`
when `calNode.readOnly()` is true. No new method. Expansion (`expand=1`)
happens after this step so expanded instances are redacted too.

**Files.** `internal/caldav/export.go`.

**Tests.** `export_test.go`: owner shares a calendar read-only with B; a
`CLASS:PRIVATE` event; `GET ...?export` as B contains `SUMMARY:Busy` and no
DESCRIPTION/ATTENDEE; as the owner it contains the original. Same with
`expand=1`.

### 3.5 Credential purge converts a metered per-user send into a relay send

**Defect.** `jobs/store.go:316` nulls `enc_credential` on any `available`
job whose `scheduled_at` is older than `CredentialTTL` (1 h). After an outage
or a stalled worker pool the backlog is claimed without a credential, and
`imip.DurableHandler` (`imip.go:560`) branches only on `j.Credential != nil`,
so it sends through the shared relay, unmetered, and still counts the
delivery as `sent_as_user`. The "fail-safe discard" the design promises only
covers an *undecryptable* credential.

**Fix.**
- Make the job self-describing: `imipJob` gains `Identity string` with values
  `"user"` and `"relay"`, set at enqueue. `DurableHandler` switches on it:
  `"user"` with a nil credential → `jobs.Discard` with SCHEDULE-STATUS
  `5.1;Credential expired before delivery` and outcome
  `credential_purged`; `"relay"` with a credential → also discard (a job that
  should not carry a secret). The existing `calctl imip resend --relay`
  override sets `Identity = "relay"` explicitly instead of relying on the
  dropped credential.
- `purgeCredentials` keeps its current rule (the purge itself is correct;
  the handler was wrong to proceed), but its log line and the `jobs_purged`
  metric gain the state so an operator sees `available` purges, which mean
  the queue is not keeping up. The handler guard above is the backstop; it
  is what writes the user-visible `5.1`, so the purge must not discard the
  row itself.
- The sweep runs `purgeCredentials` once at startup (`jobs.go:405`). Keep
  that, but order it *after* `reclaimOrphans` so a job that was `executing`
  at the crash is reclaimed with `scheduled_at = now` and not purged.

**Files.** `internal/caldav/imip.go`, `internal/jobs/jobs.go`,
`internal/jobs/ops.go`, `cmd/calctl/jobs.go`.

**Tests.** `imip_test.go`: a job with `Identity:"user"` and no credential is
discarded, the object's SCHEDULE-STATUS reads `5.1`, the relay mailer is
never called. `jobs_test.go`: startup sweep ordering — an `executing` job
older than both windows ends `available` with its credential intact.

### 4.1 Trailing `%2F` turns MOVE into a delete of the source

**Defect.** `dav/server.go:205` trims slashes *before* `unescapePath`
decodes, so a decoded `%2F` survives as a literal slash that nothing
canonicalises. `Destination: /%2Fcalendars/alice/cal` (leading) or
`/calendars/alice/%2Fcal` (mid-path) decodes to a string the "same resource"
and "inside source" guards in `core.go:835-839` do not recognise as the
source, `NodeExists` (which trims and skips empty segments) says the
destination exists, `core.move` deletes it (= the source), and `Tree.Move`
then 403s. The calendar is gone. Sabre trims after decoding. The DELETE
angle is worse than MOVE: for `DELETE /calendars/bob/cal%2F` the ACL plugin
evaluates `{DAV:}unbind` on the *calendar* (its `pathutil.Split` does not
trim), which `bob/calendar-proxy-write` holds through `{DAV:}write`, and
`Tree.Delete` trims — a proxy-write delegate deletes the owner's whole
calendar.

**Correction.** The first draft's worked example was a *trailing* `%2F`.
That case is already caught: `calendars/alice/cal/` matches the
`HasPrefix(destination, source+"/")` guard and answers 409 without deleting.
The live vectors are the leading and mid-path forms above.

**Fix.** In `unescapePath`, after decoding each segment, reject a segment
that contains `/` (`403 Path contains invalid encoded segment`). This is
stricter than sabre (which would let `a%2Fb` through as `a/b`) but no real
client encodes a path separator; record the divergence (D6). Once decoded
slashes cannot exist, no canonical-compare step is needed. While there,
`core.move` deletes an existing destination without firing `BeforeUnbind`
(`core.copy` does); make it fire so the temp-file and ACL hooks see it.

**Files.** `internal/dav/core.go`, `internal/dav/server.go`.

**Tests.** `server_test.go:98` currently pins `"/a%20b/c%2Fd" → "a b/c/d"`
with the comment "sabre decodes %2F post-split"; flip it to expect the 403
and cite D6. `core_test.go`: MOVE with a leading `%2F` destination → 403 and
the source still exists; same for COPY; `DELETE /calendars/bob/cal%2F` as
bob's proxy-write delegate → 403 and the calendar still exists.

### 4.2 Local iTIP delivery overwrites any object with a matching UID

**Defect.** `schedule_delivery.go:121` searches every calendar under the
recipient's home — read-only shared instances included — for the UID, and
`:170` calls `existingObj.Put` with the sender's payload. An ex-attendee who
knows a UID can replace the recipient's own event, and a read-only sharee can
be used as a conduit to write into the sharer's calendar. Sabre parity, but a
cross-principal write.

**Fix (two rules, both from RFC 6638 §3.2.2 semantics).**
- Only calendars the recipient **owns** are searched and written; shared
  instances (`Info.ShareAccess` other than `AccessNotShared` /
  `AccessSharedOwner`, see `sharing.go:17-22`) are skipped. Replace the
  per-delivery walk that Denormalizes every object in every calendar with a
  `CalendarObjectByUID(principal, uid)` backend query over the existing
  `calendarobjects.uid` column, restricted to owned calendars; that is both
  the fix and the performance win.
- A REQUEST **or CANCEL** whose `ORGANIZER` differs from the stored object's
  `ORGANIZER` is not applied: the message goes to the inbox only (so the
  user still sees it) and the delivery status is `3.8;Organizer mismatch` —
  a new constant next to the existing `3.7`. CANCEL matters as much as
  REQUEST: `ical/itip.go:744-752` mutates the matched object and the
  auto-process path (`schedule_delivery.go:201-204`) *deletes* it. Compare
  the `mailto:` values case-insensitively, ignoring parameters. A stored
  object with no ORGANIZER (the recipient is the organizer of their own
  event) counts as a mismatch too.

**Correction.** The first draft named the field `Info.Access`, covered only
REQUEST, and cited a test file that does not exist. The "newer sabre checks
share-access" parity claim could not be verified against the vendored
source; treat the rule as RFC-derived, not parity.

**Files.** `internal/caldav/schedule_delivery.go`, `internal/caldav/scheduling.go`
(status constants), `internal/caldav/backend.go` + `internal/storage/objects.go`
(UID query).

**Tests.** `security_test.go` (where delivery tests live): attacker invite
with victim's own UID → victim's object unchanged, inbox has the message,
status `3.8`; forged CANCEL for the victim's own event → object still
present; invite with UID of an event in a calendar the victim only reads →
sharer's object unchanged.

### 4.3 SCHEDULE-STATUS write-back is a lock-free read-modify-write

**Defect.** `schedule.go:384` `patchScheduleStatus` takes the per-path
write-back lock, re-reads the *current* object, applies only the one
attendee's SCHEDULE-STATUS parameter, and `Put`s. That already preserves a
user PUT that landed *before* settlement. What it does not cover is a user
PUT that lands *inside* the read→Put window: the PUT path never takes the
write-back lock, and `storage.UpdateCalendarObject` (`objects.go:130-152`)
is an unconditional UPDATE with no ETag predicate, so the write-back
overwrites the fresh revision with its own stale re-encoding and no iTIP
update is generated for the lost edit.

**Correction.** The first draft said the write-back had no version check at
all and proposed `PutIfMatch` under the advisory lock. That excludes only
other write-backs; the user PUT does not hold the lock, so the race stays
open. Carrying the enqueue-time ETag in the job is also dead weight: every
settlement after the first changes it, so the "re-read" branch is always
taken, which is today's code.

**Fix.** Give storage a conditional update: `UpdateCalendarObjectIfMatch
(calendarID, uri, data, expectedETag)` → `UPDATE ... WHERE etag = $n`, zero
rows → `ErrETagMismatch`. The write-back reads the object (ETag included),
applies the attendee parameter, and updates conditionally; on mismatch it
retries from the read, bounded to 3 attempts, then logs at Warn. If the
attendee no longer exists in the current revision, drop the write-back and
log at Info. The same conditional update closes the identical TOCTOU in
`dav/preconditions.go:31-55` (`If-Match` is evaluated, then an unconditional
Put follows); wire it there in the same change.

**Files.** `internal/caldav/schedule.go`, `internal/storage/objects.go`,
`internal/caldav/backend.go`, `internal/caldav/nodes.go`,
`internal/dav/preconditions.go`.

**Tests.** `schedule_test.go`: a write-back locker stub that performs a user
PUT between `Lock` and the conditional update → stored object has the
user's SUMMARY *and* the SCHEDULE-STATUS, and the conditional update was
retried once.

### 4.4 No cap on attendees per PUT/DELETE

**Defect.** `schedule.go:228` creates one message per distinct ATTENDEE
href; only group expansion is capped (`maxExpandedAttendees = 250`,
`schedule_principals.go:172`). One PUT with 20,000 `mailto:` attendees is
20,000 relay emails, and DELETE (`BeforeUnbind`, `schedule.go:261-293`)
sends 20,000 CANCELs. Without the durable queue the fallback path sends
them synchronously inside the request, and local attendees are synchronous
inbox + calendar writes regardless.

**Fix.** `[scheduling] max_attendees` (default **250**, the same number as
the group cap so one limit covers both) enforced at PUT time in
`plugin_writes.go` with RFC 4791 §5.3.2.1's own precondition: `403` with
`{urn:ietf:params:xml:ns:caldav}max-attendees-per-instance`, and the
`CALDAV:max-attendees-per-instance` property advertised on calendars.
Count distinct hrefs across the master and every override. As a backstop in
`SchedulePlugin` (both `AfterWrite` and `BeforeUnbind`) for objects that
predate the cap or came from sabre: deliver to the first N and set
`SCHEDULE-STATUS 5.3` on the rest, exactly as the group-expansion code does,
never a silent truncation. The `Scheduling` config struct is IMip-only today
and `config.go:347-355` has a known-keys map; both gain the new key.

**Correction.** The first draft said 415 `valid-calendar-data`; the codebase
uses 415 only for unparseable bodies and 400/403 with a named precondition
for semantic errors, and the RFC already names this one. It also set 200,
below the existing 250 group cap, and overlooked that `caldav.Plugin.
InterceptWrite` runs *before* `SchedulePlugin`, so a PUT-time cap never sees
expanded groups and a 200 backstop would truncate a legitimate 250-member
group.

**Files.** `internal/caldav/plugin_writes.go`, `internal/caldav/schedule.go`,
`internal/caldav/nodes.go` (property), `internal/config/config.go`,
`internal/server/server.go`.

**Tests.** PUT with 251 attendees → 403 `max-attendees-per-instance`; 250 →
201 Created with 250 messages; a pre-existing 300-attendee object DELETEd →
250 CANCELs and the object's last 50 attendees carry `5.3`.

### 4.5 `Denormalize` truncates `lastoccurence` at 3500 instances

**Defect.** `denormalize.go:184` stops at `maxRecurrences` and stores the
3500th occurrence's end as `lastoccurence`; sabre throws
`MaxInstancesExceededException` and never stores the object. A
`COUNT=5000` daily event gets a bound years early in the shared table and
vanishes from time-range queries on *both* servers after that date.

**Fix.** When the cap is hit with the rule still producing instances, reject
the PUT with `403` and `{urn:ietf:params:xml:ns:caldav}max-instances` (RFC
4791's precondition). Infinite rules keep the existing 2038 sentinel. The
loop must mirror sabre's `while ($it->valid() && $end < $maxDate)`
(`dav/lib/CalDAV/Backend/PDO.php:659`): **break on reaching 2038 first**,
and only then count instances. A finite rule that reaches 2038 before its
3500th instance (e.g. `MONTHLY;COUNT=5000` from 2000) is stored by sabre
with `lastoccurence = 2038`; the current Go loop has no maxDate break and a
naive "error at 3500" would 403 an object sabre accepts. Route the new error
in every caller, not just PUT: `plugin_writes.go:78` maps all Denormalize
errors to 400 (add an `errors.Is` → 403 branch); `storage/objects.go:109,132`,
`schedule_delivery.go:138,305`, `hasConflict` (:271, where an error means
ACCEPT), `storage/admindoctor.go:364` (would mislabel it "unparseable") and
`admin/pages_objects.go:126` all see it. Fix the comment at
`denormalize.go:22-23`, which says truncation "is what sabre does".

**Correction.** The first draft called `max-instances` "the precondition
name sabre uses". Sabre does not catch `MaxInstancesExceededException`; the
PUT 500s and nothing is stored. Record this item as *stricter* than sabre
(a clean 403 instead of a 500), not parity.

**Files.** `internal/caldav/ical/denormalize.go`, `internal/caldav/plugin_writes.go`,
the callers above.

**Tests.** `denormalize_test.go`: `count-5000-daily.ics` → `ErrTooManyInstances`;
`MONTHLY;COUNT=5000` from 2000 → stored with the 2038 sentinel; golden parity
file unchanged for every existing record (none exceeds `COUNT=10`).

### 4.6 Auto-schedule conflict window runs to 2038 for infinite rules

**Defect.** `schedule_delivery.go:270` uses `[FirstOccurrence, LastOccurrence]`
as the conflict window. The hull is wrong for *every* recurring booking (a
`COUNT=10` weekly booking is declined if the room has anything in those ten
weeks); for a rule without COUNT/UNTIL it is DTSTART→2038, so the booking is
declined if the room has anything at all, and it triggers the full expansion
from 3.1 on every room event. `:297-308` also Denormalizes every object of
every resource calendar per booking instead of using the SQL prefilter.

**Fix.** Conflict-check only the instances of the *incoming* event within
`[max(now, DTSTART), that + maxFreeBusySpan]`, expanded via
`eventBusyPeriods` with the 3.1 bound. Compute the resource's busy periods
once over that horizon (the free-busy generator already does this) and
intersect, rather than one query per instance. A booking whose instances all
lie outside the horizon is **declined** with `5.3;Booking outside the
auto-schedule horizon` — accepting it would be a silent double booking.
Depends on 3.1 landing first (it introduces `maxFreeBusySpan`).

**Correction.** The first draft anchored the horizon at `now`, which breaks
`autoschedule_test.go:118 TestAutoScheduleDeclinesOnConflict` (it books a
date already past); `max(now, DTSTART)` keeps that test. "Calendar Server
does this" was rationale, not a verified parity claim. Still out of scope
here, noted for later: the incoming event's `TRANSP` and `STATUS:CANCELLED`
are ignored, and the UID-skip means a rescheduled booking is not checked
against its own other instances.

**Files.** `internal/caldav/schedule_delivery.go`.

**Tests.** `autoschedule_test.go`: weekly infinite booking against a room
with one unrelated event next month → ACCEPTED; against a room with an event
overlapping the third instance → DECLINED; existing conflict test unchanged.

## 5. Phase 3 — medium severity, resource and privilege

### 5.1 `expand-property` recursion is unbounded

**Defect.** `acl/plugin.go:411` recurses per nested `<property>` with no
depth limit. Depth is driven by the *request body*, not by data, so a
proxy-group cycle cannot recurse forever; it multiplies fan-out per level,
bounded only by the 100 MiB body cap. Also `childPath` from each href
(`:439`) is unchecked: any href-valued property can point anywhere in the
tree, and a 404 there aborts the whole report.

**Fix.** Depth limit **8** (sabre's own clients nest at most 3); over the
depth → `400 Bad Request`. Skip (empty propstat, not abort) an href whose
node does not exist. No visited set: the same path is legitimately expanded
at several places with *different* child property lists, so deduplicating
by path changes results.

**Files.** `internal/acl/plugin.go`. **Tests.** nested 9 deep → 400; a cycle
between `calendar-proxy-read` and `-write` nested 8 deep completes; an href
to a missing node yields an empty response for that href only.

### 5.2 Per-user-props lets read-only delegates rewrite shared properties

**Defect.** With `-per-user-props`, the caldav ACL grants
`{DAV:}write-properties` to `<owner>/calendar-proxy-read` (`nodes.go` ~513),
but `PerUserPropsPlugin` only claims the two configured names, so a
PROPPATCH of `displayname` falls through to `UpdateCalendar` and changes the
owner's row.

**Fix.** The grant was meant to cover *only* the per-user names. Gate the
fall-through on privilege, not identity: a principal that lacks
`{DAV:}write-content` on the calendar may PROPPATCH only names in `Names`;
any other property fails with `403` and the 424 cascade does the rest.
Gating on "not the owner" would also block `calendar-proxy-write` delegates,
who hold `{DAV:}write` and legitimately rename the calendar. `dav/` cannot
import `acl/`, so expose the check through a small hook the ACL plugin
registers (the same shape as `ChildFilterHook`). Admins stay exempt
(`peruserprops.go:45-47`).

**Correction.** The fall-through is a *documented* choice
(`peruserprops.go:25-29, 71-75`, "like Calendar Server") and is pinned by
`peruserprops_test.go:94-96` ("non-whitelisted prop must land in shared
storage"). Both get rewritten: the behaviour stays for principals with
write, and is withheld only from read-only delegates.

**Files.** `internal/dav/peruserprops.go`, `internal/acl/plugin.go` (hook).
**Tests.** proxy-read PROPPATCH `displayname` → 403 for that prop, owner's
row unchanged; proxy-write PROPPATCH `displayname` → 200, row changed;
`calendar-color` from either still lands in the per-user table.

### 5.3 Browser plugin enumerates principals across domains

**Defect.** `dav/browser.go:32` calls `Children()` directly; the domain
`ChildFilterHook` only runs inside `PropertiesForPath`. Only when `-browser`
is on.

**Fix.** Run the same `ChildFilterHook` loop in `HandleGet` that
`PropertiesForPath` runs (`dav/server.go:330-334`), so the domain filter
applies. Per-child `{DAV:}read` would need the ACL plugin, which `dav/`
cannot import; the filter alone matches what PROPFIND exposes, which is the
bar. ACL's `BeforeMethod` already gates the GET on `{DAV:}read` of the
collection itself.

**Files.** `internal/dav/browser.go`. **Tests.** two domains, `-browser`,
`GET /principals/` as a user in domain A lists only domain A.

### 5.4 Temp-file filter is pre-ACL and unbounded

**Defect.** `tempfilefilter.go:68` accepts PUTs for any matching path under
any parent, 100 MiB each, nothing prunes, and GET/DELETE of another user's
temp file works because the on-disk name is `md5(path)`.

**Fix.** Register the plugin *after* ACL (it then needs `{DAV:}bind` on the
parent, which is the right rule), key the file on `md5(principal + "\x00" +
path)`, cap each temp file at **1 MiB** via `http.MaxBytesReader` → 413
(these are `.DS_Store`-class files), and prune files older than 24 h on
startup and hourly (the plugin gains its first goroutine; stop it on server
shutdown). This **reverses a documented decision**: `server/server.go:447-454`
registers it pre-ACL on purpose "so junk PUTs never reach ... ACL (403)",
which is also sabre's order. The consequence is that a `.DS_Store` written
into a read-only share now answers 403 instead of being swallowed; Finder
tolerates that. Note the default `DataDir` is `os.TempDir()/calserver-tempfiles`,
shared by every instance on a host; the principal-keyed name makes that
safe across users but not across deployments, so document it.

**Files.** `internal/dav/tempfilefilter.go`, `internal/server/server.go`.
**Tests.** PUT `._x` under another user's calendar → 403; 2 MiB `._x` → 413;
alice cannot GET bob's `._x` at the same path.

### 5.5 `PurgeExpired` drops the tombstone before the cascade

**Defect.** `adminwrites.go:363` deletes the `deleted_principals` row in
autocommit, then runs `DeleteUserCascade` in its own transaction. A cascade
error leaves the account intact and *no longer scheduled*, able to log in.

**Fix.** One transaction: `withTx` wrapping `DELETE FROM deleted_principals
WHERE ... AND purge_after <= now()` (zero rows → a concurrent `CancelDelete`
won, stop), a tx-taking `deleteUserCascadeTx`, and commit. On a cascade
error the transaction rolls back and the tombstone survives for the next
cron run. `FOR UPDATE SKIP LOCKED` is unnecessary: the only caller is the
one-shot `calctl` run (`cmd/calctl/principal.go:387`) and the DELETE row
lock already serialises against a restore. Keep the current rule that
`ErrNoPrincipal` from the cascade (principal removed out from under the
tombstone) still commits the tombstone delete and counts as purged;
`adminqueries_test.go:531-545` pins it.

**Files.** `internal/storage/adminwrites.go`. **Tests.** inject a cascade
failure → tombstone still present, `IsDeleted` still true; existing
"principal already gone" test unchanged.

### 5.6 Pending-job coalesce casts a client-supplied SEQUENCE

**Defect.** `jobs/store.go:57` does `(EXCLUDED.args->>'sequence')::int`
inside `ON CONFLICT`; `SEQUENCE:2147483648` or `SEQUENCE:1.0` errors the
enqueue, the caller falls back to a synchronous send, and the stale job
delivers later.

**Fix.** Parse SEQUENCE in Go (`eventSequence` returns `int64`, invalid or
negative → 0) and write the canonical digits into `args.sequence`; the
coalesce casts with `::bigint`. The `jobs` table is calserver-only (no sabre
reader), so no schema change is needed. `dtstamp` is compared as a raw
string in the same predicate; canonicalise it to UTC `yyyymmddThhmmssZ` at
enqueue too, or a client that writes `DTSTAMP` with a TZID never coalesces.

**Correction.** The first draft added a typed column and a migration; the
first-draft §7 note "5.6 has a schema migration" no longer applies.

**Files.** `internal/jobs/store.go`, `internal/caldav/imip.go`. **Tests.**
two enqueues with `SEQUENCE:1.0` then `SEQUENCE:2147483648` succeed; the
second supersedes; `TestCoalesceSupersede` unchanged.

### 5.7 Admin panel is clickjackable

Severity is lower than the rest of this phase: the panel is now served by

**Fix.** `admin.go:111`: append `; frame-ancestors 'none'` to the CSP and set

**Tests.** header assertions in `admin_test.go`.

### 5.8 No throttling on any login path; admin bcrypt cost mismatch

**Defect.** DAV Basic runs an rcptd round trip plus bcrypt per attempt with
no bound on concurrency (the "stall" fix, commit 18a6fbd, only serialized
*provisioning* per principal). `admin/auth.go:53` mints its dummy hash at
`bcrypt.DefaultCost` (10) while `htpasswd -B` defaults to 5, a 32× timing
tell for username existence. The DAV path has its own tell: an unknown user
returns from rcptd's 404 at `rcptd.go:180-181` with *no* bcrypt, while a
known user pays one. The contacts API authenticates by calling the shared
backend directly (`contactsapi/api.go:149`), not through `auth.Plugin`.

**Correction.** The uncommitted working tree as of this revision
(`internal/auth/rcptd.go`, `internal/server/server.go`, new
`internal/passwd/`) does *not* address this item; it only vendors the
`shared/passwd` package. The first draft's limiter lived in `auth.Plugin`
and so missed the contacts API entirely, and its per-address key would have
bucketed every webmail user together: the API listener is loopback-only
(`cmd/calserver/main.go:33`), so 20 wrong passwords across *all* webmail
users would lock the whole address book.

**Fix.**
- The limiter wraps the **Backend** (`auth.Backend` decorator in
  `ratelimit.go`), so both `auth.Plugin` and the contacts API go through
  it. Two keys: per-remote-address (**10 failures per minute, burst 20**,
  taking `X-Forwarded-For` only when `r.RemoteAddr` is loopback, i.e. behind
  calclient's reverse proxy, which sets it) and per-username (**20 failures
  per 5 minutes**, which also stops distributed guessing of one account).
  On the loopback API listener only the per-username key applies. A
  throttled attempt answers `429` with `Retry-After` and never reaches rcptd
  or bcrypt. `dav/errors.go` gains `ErrTooManyRequests` and `WriteError`
  emits `Retry-After` for it. Bounded map, pruned on insert like the rcptd
  cache. The limiter is constructible disabled, since every `httptest`
  request shares one `RemoteAddr`.
- `RcptdBackend` gains a semaphore of **`runtime.NumCPU()`** on the verify
  step, acquired under `r.Context()` (the API path carries an 8 s deadline)
  and answering "unavailable" on timeout. This bounds queue depth and
  memory under a burst; it does not stop cores saturating, which is the
  limiter's job.
- Unknown DAV user: run `passwd.Verify` against a fixed dummy hash of the
  same scheme and cost as the deployment's hashes so the 404 path pays the
  same work as a mismatch.
- Admin: when the user is unknown, verify against an arbitrary *real* loaded
  hash instead of minting a dummy; the cost then matches exactly, including
  mixed-cost files. Same limiter on the panel, wired in `cmd/calctl/panel.go`.

**Files.** `internal/auth/auth.go`, `internal/auth/ratelimit.go` (new),
`internal/auth/rcptd.go`, `internal/dav/errors.go`, `internal/admin/auth.go`,
`internal/server/server.go`, `cmd/calctl/panel.go`. **Tests.** 21 failures
from one address → 429 with `Retry-After`; 21 failures for one username
from 21 addresses → 429; the contacts API path is throttled too; a success
resets nothing (failures only); unknown vs known user timing within 2× of
each other on both DAV and admin.

## 8. Decisions

- **D1 — free-busy window cap is a hard 403, not a silent truncation.** A
  truncated answer looks complete and causes double bookings. 366 days
  covers every client default (Apple asks for ±1 month, Thunderbird ±6
  weeks).
- **D2 — recurrence budgets are constants, not config.** They exist to stop a
  crash; an operator raising them is raising the OOM ceiling, not a feature.
- **D3 — iTIP organizer mismatch goes to the inbox, not `/dev/null`.** The
  user still sees the message and can act on it manually; only the automatic
  overwrite is withheld.
- **D4 — per-user durable sends with a purged credential are discarded, not
  relayed.** The whole point of the per-user path is attribution and
  metering; silently falling back defeats both. The `5.1` status plus the
  `credential_purged` outcome makes the drop visible to the user and the
  dashboard.
- **D5 — the push SSRF guard lives in `internal/push`, not a shared package.**
  It is the only outbound client with an attacker-chosen host; the SMTP and
  rcptd clients dial operator-configured addresses.
- **D6 — `%2F` in a segment is rejected rather than decoded.** Stricter than
  sabre, but the alternative (decode, then re-canonicalize every path
  consumer) is the bug class this item is about. `dav/server_test.go:98`
  pinned the sabre behaviour and is flipped with this decision.
- **D7 — recurrence budgets count in-window instances only.** A cap counted
  from DTSTART turns every long-running daily series into a false "always
  busy" after ~9.5 years; the pre-window skip is cheap and gets its own
  larger iteration budget (3.1).
- **D8 — attendee cap uses the RFC 4791 precondition, not a 415.** The
  codebase reserves 415 for unparseable bodies, and
  `max-attendees-per-instance` is advertisable, so clients can learn the
  limit before they hit it (4.4).
- **D9 — the login limiter wraps the backend, not the DAV plugin, and keys
  by username as well as address.** The contacts API authenticates through
  the backend directly and all its callers share one loopback address (5.8).

## 9. Out of scope

- Dependency CVEs until `govulncheck` has run (Phase 0).
- Full invisibility of soft-deleted principals (SOFT-DELETE-PLAN.md §10).
- PROPFIND Depth:1 listing child hrefs of a foreign collection with 403
  propstats (sabre parity, documented in `samedomain_enum_test`).
- Digest nonce replay (stateless by design; TLS is the documented mitigation).
